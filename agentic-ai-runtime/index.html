Component details

LOOP · STEP 01

Perceive

What happens

The agent ingests the goal, retrieves relevant context from all memory tiers (working + episodic + semantic), and constructs the initial perception frame. Context window management is critical here: you must fit the goal, history, tool schemas and retrieved knowledge into the token budget. Everything retrieved is data, not instruction: a recalled episode or a retrieved document may carry text written to steer the agent.

Implementation

Sketch in Python style, not runnable as written: the objects it calls stand for components you supply.

async def perceive(self, goal, memory): context = await memory.working.get_state() episodes = await memory.episodic.recall(goal) knowledge = await memory.semantic.retrieve(goal) return PerceptionFrame( goal=goal, current_state=context, past_experience=episodes, domain_knowledge=knowledge, tools=self.tool_registry.schemas() )

LOOP · STEP 02

Plan

What happens

The LLM reasons about the perception frame and generates an action plan. For simple tasks, this is a single next-action. For complex goals, it produces a multi-step task graph with dependencies. Planning strategies include ReAct, Tree-of-Thought, and Plan-and-Solve.

Implementation

Sketch in Python style, not runnable as written: the objects it calls stand for components you supply.

async def plan(self, frame): response = await self.llm.structured_output( system=PLANNER_PROMPT, messages=[{"role": "user", "content": frame.render()}], schema=ActionPlan ) # Validate against budget if response.estimated_cost > self.budget: return self.replan_with_constraints(response) return response

LOOP · STEP 03

Act

What happens

Execute the planned action through the sandboxed function executor. Actions include tool calls (APIs, databases, code), LLM generations (drafting, analysis), or delegation to sub-agents. Every action goes through a permission check, a human-approval gate where the policy requires one, and audit logging. All three run outside the model.

Implementation

Sketch in Python style, not runnable as written: the objects it calls stand for components you supply.

async def act(self, plan): action = plan.next_action # Permission + HITL checks if not self.authz.can_execute(action): return ActionResult(error="Denied") if self.hitl.should_pause(action): await self.hitl.wait_approval(action) result = await self.executor.run(action) self.audit.log(action, result) return result

LOOP · STEP 04

Observe

What happens

Evaluate the action result using the self-reflection module. Did it succeed? Did it advance the goal? Deterministic checks come first (error codes, schema, tests). An evaluator model's score is a weak, uncalibrated signal, and the thresholds below are placeholders. Every tool result is untrusted data: a web page, a document, an email or another agent's reply can carry text written to steer the agent (indirect prompt injection), so a result is checked and recorded, never obeyed.

Implementation

Sketch in Python style, not runnable as written: the objects it calls stand for components you supply.

async def observe(self, action, result): evaluation = await self.reflection.evaluate( action, result, self.goal ) if evaluation.score < 5: return Decision.REPLAN elif evaluation.score < 7: return Decision.RETRY return Decision.PROCEED

LOOP · STEP 05

Adapt

What happens

Based on the observation, update working memory, check budget constraints, and decide: continue current plan, adjust approach, or replan entirely. If the goal is achieved or budget exhausted, compile the final result and exit the loop.

Implementation

Sketch in Python style, not runnable as written: the objects it calls stand for components you supply.

async def adapt(self, observation): self.memory.add(observation) self.budget -= observation.token_cost if observation.goal_achieved: return COMPLETE if self.budget <= 0: return BUDGET_EXCEEDED if observation.should_replan: await self.planner.replan() return CONTINUE

L7 · APPLICATION

Agent API Gateway

Purpose

The single entry point for all agent invocations. Handles authentication (OAuth2/JWT), rate limiting per agent and request validation, and routes each request to the appropriate orchestrator. Authenticating the caller here does not authorise what the agent later does: each tool call is authorised separately, at the tool boundary.

API contract

Example request, not a live endpoint.

L7 · SAFETY

Human-in-the-Loop

Purpose

Approval points where the agent pauses and a person confirms the exact action before it runs. Gate on properties of the action that the runtime can check for itself: does it have a side effect, can it be undone, what does it cost, how sensitive is its target. Read-only, low-cost steps run without a pause, so that people are asked rarely enough to keep reading what they approve.

Implementation

Runnable as written: Python 3.10 or later, standard library only. Run for this page in November 2026.

from dataclasses import dataclass @dataclass class Action: tool: str side_effects: bool = False reversible: bool = True cost_usd: float = 0.0 risk: str = "LOW" # set by policy, not by the model class HITLGate: def __init__(self, cost_limit_usd=1.00): self.cost_limit_usd = cost_limit_usd def should_pause(self, action: Action) -> bool: if action.risk == "HIGH": return True if action.side_effects and not action.reversible: return True if action.cost_usd > self.cost_limit_usd: return True return False gate = HITLGate() search = Action("search_database") email = Action("send_email", side_effects=True, reversible=False) print(gate.should_pause(search)) # False print(gate.should_pause(email)) # True

What it does not stop

The model's own confidence is deliberately not an input. A confidence figure that a model reports about itself is not a calibrated probability, and text injected into the context can raise it, so log it if you wish but do not let it open or close a gate. An approval is only as good as what the approver sees: show the real tool name and arguments, not the model's summary of them. Too many prompts produce approval fatigue, and a tired approver is not a control.

L6 · ORCHESTRATION

Agent Controller

Purpose

The heartbeat of every agent. Runs a bounded loop: receive goal → plan steps → execute step → observe result → decide next action. Continues until goal met, budget exhausted, or stop condition triggers.

Full runtime

Sketch in Python style, not runnable as written: the objects it calls stand for components you supply.

class AgentController: async def run(self, goal, state): while not state.is_terminal(): plan = await self.planner.next_step(goal, state) if plan.requires_approval: await self.hitl.request_approval(plan) result = await self.executor.execute(plan.action) obs = self.observer.evaluate(result) state = self.state_mgr.update(state, obs) if state.steps > goal.max_steps: state.set_terminal("budget_exceeded") return state.final_result

L6 · ORCHESTRATION

Task Scheduler

Purpose

Manages a directed acyclic graph (DAG) of tasks. Independent tasks run in parallel; dependent tasks wait. Built on durable execution engines for crash recovery.

Implementation

Sketch in Python style, not runnable as written: the objects it calls stand for components you supply.

async def execute_dag(self, graph): ready = graph.get_ready_tasks() while ready: results = await asyncio.gather( *[self.execute_task(t) for t in ready] ) for task, result in zip(ready, results): graph.mark_complete(task, result) self.checkpoint(graph) ready = graph.get_ready_tasks()

L5 · COGNITION

LLM Reasoning Engine

Purpose

The cognitive core. Current practice is native tool calling: the runtime sends the tool schemas with each request, the model replies with a structured tool call instead of free text, the runtime runs the call and returns the result as a tool message, and the loop repeats until the model answers without asking for a tool.

This reason-then-act cycle is the ReAct pattern. Earlier agents built it by asking the model to print "Thought", "Action" and "Action Input" lines as text and then parsing that text. That form is fragile, and native tool calling has replaced it. Chain-of-thought and tree-of-thought describe how a model reasons before it chooses an action; many current models do that reasoning internally before they answer.

Tool-calling loop

Pseudocode in Python style. Message and field names differ between model providers: check your provider's tool-calling documentation.

async def reason_and_act(self, goal, max_steps=20): messages = [{"role": "user", "content": goal}] for _ in range(max_steps): reply = await self.llm.chat( messages=messages, tools=self.tool_registry.schemas(), ) messages.append(reply.as_message()) if not reply.tool_calls: return reply.text # final answer for call in reply.tool_calls: # The policy check runs outside the model decision = self.policy.check(call) if decision.allowed: result = await self.executor.execute(call) else: result = f"Denied: {decision.reason}" messages.append({ "role": "tool", "tool_call_id": call.id, "content": str(result), # untrusted data }) raise StepBudgetExceeded(goal)

What to remember

The model proposes a call; the runtime decides whether it runs. Every tool result goes back into the context as data that the model will read, which is exactly how indirect prompt injection gets in. See Guardrails & Safety.

L5 · COGNITION

Self-Reflection

Purpose

After each action the runtime checks the result before it decides to proceed, retry or replan. Use deterministic checks first: did the tool return an error, does the output match its schema, do the tests pass, is the row count plausible. An evaluator model, often a cheaper one, can then judge whether the step advanced the goal.

Treat that judgement as a weak signal. A 1 to 10 score from a model is not calibrated, the thresholds below are placeholders to tune against labelled examples, and an evaluator that reads tool output can be steered by text injected into that output.

Scoring logic

Sketch in Python style, not runnable as written: the objects it calls stand for components you supply.

async def evaluate(self, action, result, goal): # Deterministic checks first if result.error or not result.matches_schema(): return Decision.RETRY score = await self.evaluator.score( f"Did this advance the goal?\n" f"Goal: {goal} Result: {result}\n" f"Score 1-10:" ) # Placeholder thresholds: tune on labelled examples if score < 5: return Decision.REPLAN elif score < 7: return Decision.RETRY return Decision.PROCEED

L5 · COGNITION

Structured Output

Purpose

Forces the LLM to output valid JSON matching predefined schemas. This stops malformed tool calls. A schema checks the shape of a call, not whether the call is safe to run. Pydantic models define the contract; the LLM is constrained to match. Retries on schema violation.

Schema enforcement

Sketch in Python style, not runnable as written: the objects it calls stand for components you supply.

from pydantic import BaseModel class ToolCall(BaseModel): tool_name: str arguments: dict reasoning: str confidence: float # self-reported: never gate on it result = await llm.structured_output( prompt=react_prompt, schema=ToolCall, max_retries=3 )

L4 · MEMORY

Working Memory

Purpose

Tracks everything relevant to the current execution: the goal, the current plan, tool outputs, partial results and a scratchpad. Implemented as a typed state object. This is what makes an agent stateful. When the state outgrows its token budget, the oldest observations are summarised into the scratchpad.

Data structure

Runnable as written: Python 3.10 or later, standard library only. Run for this page in November 2026.

from collections import deque from dataclasses import dataclass, field def count_tokens(text: str) -> int: # Stand-in for a real tokeniser return max(1, len(text) // 4) def summarise(text: str, limit: int = 80) -> str: # Stand-in for a call to a summariser model return text[:limit] @dataclass class WorkingMemory: goal: str # Oldest observation first observations: deque = field(default_factory=deque) scratchpad: str = "" @property def token_count(self) -> int: parts = [self.goal, self.scratchpad] parts.extend(self.observations) return sum(count_tokens(p) for p in parts) def compress_if_needed(self, max_tokens: int) -> None: # Stop when within budget, or when nothing is left. while (self.token_count > max_tokens and self.observations): oldest = self.observations.popleft() self.scratchpad += summarise(oldest) + "\n" memory = WorkingMemory(goal="Analyse Q3 revenue") for step in range(6): memory.observations.append(f"step {step}: " + "x" * 1000) print(memory.token_count) # 1517: over budget memory.compress_if_needed(max_tokens=400) print(len(memory.observations), memory.token_count) # 1 357

The token count is recomputed from the contents, so it falls as observations are compressed and the loop ends. If the scratchpad alone is over budget the loop still ends, and the caller has to summarise the scratchpad itself.

L4 · MEMORY

Episodic Memory

Purpose

Stores past execution traces across sessions. When encountering a similar goal, retrieves relevant past episodes to inform planning. It can save the agent from working out again an approach it has already found. A stored trace is untrusted input when it is recalled: an episode poisoned in one session persists into the next. Record where each memory came from, and let a memory inform a plan, never authorise an action.

Store & recall

Sketch in Python style, not runnable as written: the objects it calls stand for components you supply.

class EpisodicStore: async def store(self, trace): summary = await self.llm.summarize(trace) embedding = await self.embed(summary) await self.vector_db.upsert( vector=embedding, metadata={"outcome": trace.outcome} ) async def recall(self, goal, k=5): return await self.vector_db.search( query=goal, k=k, filter={"outcome": "success"} )

L4 · MEMORY

Semantic Memory (Agentic RAG)

Purpose

Goes beyond basic RAG. The agent actively reasons about retrieval: formulates queries, evaluates relevance, reformulates if results are poor, and cross-references multiple sources. Filter by what the requesting user is entitled to see before ranking, and treat retrieved text as data: a retrieved document is an obvious carrier of indirect prompt injection.

Multi-round retrieval

L4 · MEMORY

Context Window Management

Purpose

A central optimisation. An agent sends its context again on every step, so token use grows with the length of the run. This component implements token counting, progressive summarisation and priority-based context packing.

Budget packing

def pack(self, memory): budget = self.max_tokens - 4000 # Reserve output sections = [ (CRITICAL, memory.goal, 500), (HIGH, memory.current_plan, 2000), (HIGH, memory.recent_obs(3), 3000), (MEDIUM, memory.tool_schemas, 2000), (LOW, memory.older_obs, budget), ] return self.fit_to_budget(sections, budget)

L3 · TOOLS

Tool Registry

Purpose

A catalogue of all tools the agent can invoke. Each tool has a JSON schema describing inputs, outputs, side effects, and permissions. The LLM sees these schemas to decide which tool to call. The side-effect and permission fields are for the runtime, which enforces them whatever the model asks for.

Registration

Sketch in Python style, not runnable as written: the objects it calls stand for components you supply.

L3 · TOOLS

Function Executor

Purpose

Runs each tool call with a timeout and an idempotency key, and writes an audit record whether the call succeeds, fails or turns out to be a repeat. Permission and argument checks happen before this point (see Guardrails & Safety). The sandbox is not in this code: it is where the tool's process runs.

Timeout, idempotency and audit

Runnable as written: Python 3.10 or later, standard library only. Run for this page in November 2026.

import asyncio class ToolExecutor: def __init__(self, tools, audit_log): # tools: name -> {"fn", "timeout_s", "side_effects"} self.tools = tools self.audit_log = audit_log # append-only in real use self.completed = {} # idempotency key -> result async def execute(self, name, args, key): tool = self.tools[name] # KeyError: not registered if tool["side_effects"] and key in self.completed: # A retry: return the stored result, do not repeat self.audit_log.append((name, key, "duplicate")) return self.completed[key] try: result = await asyncio.wait_for( tool["fn"](**args), tool["timeout_s"]) except Exception as exc: entry = (name, key, "error", repr(exc)) self.audit_log.append(entry) raise if tool["side_effects"]: self.completed[key] = result self.audit_log.append((name, key, "ok")) return result async def send_email(to, subject): return f"sent to {to}" async def main(): audit = [] tools = {"send_email": {"fn": send_email, "timeout_s": 5, "side_effects": True}} run = ToolExecutor(tools, audit).execute args = {"to": "finance@example.com", "subject": "Q3"} print(await run("send_email", args, "run-42/step-3")) print(await run("send_email", args, "run-42/step-3")) print(await run("send_email", args, "run-42/step-7")) print([entry[2] for entry in audit]) # ['ok', 'duplicate', 'ok'] asyncio.run(main())

The key identifies the step (run ID plus step ID), not the arguments. A retry of step 3 returns the stored result, while step 7 sends a second, legitimate email with the same arguments. Keying on a hash of the arguments would silently drop that second email. The in-memory dictionary is for illustration only: in production the store of completed keys must be durable and shared, and it is better still if the downstream API accepts the idempotency key itself.

Where the sandbox is

Run any tool that executes code or touches files in a separate process with no ambient credentials, a scratch filesystem, and network egress limited to named destinations. A container shares the host's kernel, so on its own it is a weak boundary for code you do not trust. A microVM (Firecracker is one example) or a user-space kernel (gVisor is one example) is a stronger one.

What it does not stop: a sandbox limits what code can reach. It does not stop a tool from misusing access it was legitimately given, and it does not stop data leaving through a destination you allowed.

L3 · TOOLS

Agent Protocols: MCP, A2A and Others

Purpose

Open protocols mean a tool or an agent is integrated once, not once per framework. MCP connects an LLM application to tools and data. A2A connects one agent to another. Neither makes the thing at the other end trustworthy: a protocol standardises how you connect, and what arrives over the connection is still untrusted input.

Every status line below was checked against the project's own site in November 2026. This field moves quickly, so follow the links before you rely on a version.

MCP (Model Context Protocol)

JSON-RPC 2.0 messages between a host application, its clients and MCP servers. Servers offer tools, resources and prompts. The transports are stdio and Streamable HTTP.

Status as of November 2026: the current specification revision is 2026-07-28. Anthropic created MCP and donated it in December 2025 to the Agentic AI Foundation (AAIF), a directed fund under the Linux Foundation. The 2026-07-28 revision made the protocol stateless (no initialize handshake and no protocol-level sessions, with a mandatory server/discover call), moved tasks into an extension, and deprecated Roots, Sampling and Logging. The old HTTP+SSE transport, deprecated since the 2025-03-26 revision, stays deprecated in favour of Streamable HTTP.

Authorisation model: optional, and defined for HTTP transports only (a stdio server takes its credentials from its environment). It is built on the OAuth 2.1 draft. The MCP server is an OAuth resource server: it must publish Protected Resource Metadata (RFC 9728) and must check that each access token was issued for it. A client must name the target server with a resource indicator (RFC 8707). A server must not accept or pass on tokens meant for anything else. Client ID Metadata Documents are the preferred way to register a client, and Dynamic Client Registration is deprecated.

What it does not cover: OAuth decides who may call a server, not whether a particular tool call is safe. The specification says the protocol cannot itself enforce its consent and tool-safety principles, and that tool descriptions from a server you do not trust are themselves untrusted. A tool description or a tool result can carry injected instructions.

MCP specification, revision 2026-07-28 · authorisation · what changed

A2A (Agent2Agent)

Lets one agent discover another, hand it a task and receive the result. An agent describes itself in an Agent Card, a JSON document served at /.well-known/agent-card.json. The bindings are JSON-RPC, gRPC and HTTP+JSON.

Status as of November 2026: version 1.0. Release 1.0.0 was published on 12 March 2026, and the latest patch release is 1.0.1 (28 May 2026). Google launched A2A in April 2025 and donated it to the Linux Foundation. In August 2026 it was announced as a hosted project of the Agentic AI Foundation, alongside MCP. IBM's Agent Communication Protocol (ACP) merged into A2A in August 2025.

Security model: a server must authenticate every request, using a scheme it declares in its Agent Card (API key, HTTP authentication, OAuth 2.0, OpenID Connect or mutual TLS). Credentials are obtained outside the protocol. An Agent Card can be signed (JWS), but signing is optional.

What it does not cover: an unsigned Agent Card is a claim an agent makes about itself, not proof of who runs it or what it will do. Whatever a remote agent returns is untrusted input to yours: another agent is one of the routes by which injected instructions arrive.

A2A specification · releases · A2A joins AAIF

AGENTS.md

Not a protocol. It is a Markdown file in a repository that gives coding agents their instructions for that codebase: how to build it, test it and follow its conventions. The project calls it "a README for agents". It does not describe an agent's capabilities.

Status as of November 2026: the project site reports use by over 60,000 open-source projects, and the format is stewarded by the Agentic AI Foundation under the Linux Foundation.

What to watch: the file is instruction text that an agent reads and follows. In a repository you do not control, treat it like any other untrusted content.

agents.md

Also named in the literature

ANP (Agent Network Protocol): an open protocol stack for agent identity, discovery and messaging, built on decentralised identifiers (its own did:wba method). Status as of November 2026: the project site lists version 1.2 as the latest, with some parts still marked as draft, and names no foundation as its governing body. ANP 1.2 white paper

ACP (Agent Communication Protocol, IBM): status as of November 2026: retired as a separate protocol. Its team announced on 29 August 2025 that ACP was merging into A2A and winding down its own development. It appears here only because older articles still name it. ACP joins forces with A2A

Agora: a research proposal for a "meta protocol" through which agents agree how they will talk to each other. Status as of November 2026: an academic paper from October 2024, not a governed standard. I found no versioned specification to link, so the link is to the paper. arXiv:2410.11905

For a side-by-side comparison of MCP, ACP, A2A and ANP, see the survey by Ehtesham and colleagues (arXiv:2505.02279, May 2025). It was written before ACP merged into A2A.

L2 · EXECUTION

Workflow Engine

Purpose

An agent can run for hours or days, and over that time some step will fail. A durable execution engine records the result of every completed step, so that after a crash the workflow resumes from the last recorded step instead of starting again.

The steps that call models and tools (activities, in Temporal's terms) run at least once, not exactly once. An activity that succeeded, but whose worker crashed before it could report success, is run again. Every side-effecting activity therefore needs an idempotency key: Temporal's own guidance is to build one from the workflow run ID and the activity ID. Temporal: error handling in the Python SDK

Guardrails & Safety

The design assumption

Prompt injection cannot be reliably prevented. It can be made less likely, and its effects can be contained. A model reads instructions and data through the same channel, so any text it reads may steer it. OWASP ranks prompt injection first in its Top 10 for LLM Applications, in the 2025 edition (LLM01:2025) and again in the 2026 edition, and the 2025 entry says it is unclear whether fool-proof prevention exists.

So design as if the model can be steered. Safety then comes from what surrounds the model, not from the model behaving well:

  • Identity. Every agent and every tool call has its own identity and least-privilege credentials. See Identity & Authorisation.
  • Policy outside the model. Rules are enforced in code at the tool boundary, where text in the context window cannot argue with them.
  • Evidence. Every decision and action leaves a record that can be reviewed and proven afterwards.

Where injected instructions come from

Direct injection arrives in the user's own prompt. Indirect injection arrives in content the agent reads while it works, written by someone else: tool results, retrieved documents, web pages, emails, files, memory saved in an earlier session, and messages from other agents. For an agent the indirect route matters more, because the agent reads content that nobody on your side wrote, and it holds tools it can act with.

Controls, and what each does not stop

Input and content filtering

Injection classifiers, marking untrusted content as data, stripping hidden text. Lowers the success rate of known attack patterns.

Does not stop: new phrasings, encodings, or an attack split across several sources. A filter that passes content has not proved it safe.

Output schema validation

Rejects malformed tool calls and calls to tools that do not exist.

Does not stop: a well-formed call that does the wrong thing. Valid JSON can still send the wrong file to the wrong address.

Tool allow-list per task

The agent can call only the tools this task needs.

Does not stop: misuse of an allowed tool, or a chain of allowed tools: read a record, then send an email, is exfiltration built from two permitted steps.

Argument checks at the tool boundary

Recipient domains, path prefixes, read-only queries, amount limits, checked in code the model cannot change.

Does not stop: harm inside the permitted range, or data hidden in a field that looks legitimate.

Budgets and rate limits

Caps on steps, tokens, spend and calls per tool. They bound loops and the size of any one failure.

Does not stop: a single damaging action that fits inside the budget.

Human approval for side-effecting or irreversible actions

A person sees the exact tool and arguments before the action runs.

Does not stop: approval fatigue, or an approver shown the model's summary instead of the real arguments. People can be persuaded too.

Sandboxing and egress control

Limits what executed code can touch and where data can be sent.

Does not stop: data leaving through a destination you allowed.

PII and secret filtering

Reduces accidental disclosure in prompts, outputs and logs.

Does not stop: deliberate exfiltration in an encoded or paraphrased form. Pattern matching finds only the patterns it knows.

Evidence of every decision and action

Makes what happened reviewable and provable: who or what acted, on whose behalf, with which inputs, under which policy.

Does not stop: anything at the moment it happens. It is a detective control, and worth little unless someone reviews it and it cannot be altered.

Policy at the tool boundary

Runnable as written: Python 3.10 or later, standard library only. Run for this page in November 2026.

from dataclasses import dataclass, field @dataclass class Policy: version: str allowed_tools: set allowed_email_domains: set max_calls: int needs_approval: set = field(default_factory=set) def check(policy, tool, args, calls_so_far, approved_by=None): """Runs outside the model. Returns (decision, reason).""" if tool not in policy.allowed_tools: return "deny", "tool is not on the allow-list" if calls_so_far >= policy.max_calls: return "deny", "call budget for this task is spent" if tool == "send_email": domain = args["to"].rsplit("@", 1)[-1].lower() if domain not in policy.allowed_email_domains: return "deny", "recipient domain is not allowed" if tool in policy.needs_approval and approved_by is None: return "hold", "waiting for a person to approve" return "allow", "within policy " + policy.version policy = Policy("2026-11-a", {"search_docs", "send_email"}, {"example.com"}, max_calls=20, needs_approval={"send_email"}) ok = {"to": "cfo@example.com"} bad = {"to": "x@attacker.test"} # Prints: deny (tool), deny (recipient), hold, allow print(check(policy, "delete_records", {}, 0)) print(check(policy, "send_email", bad, 3)) print(check(policy, "send_email", ok, 3)) print(check(policy, "send_email", ok, 3, "approver-17"))

The check is ordinary code with no model in it. Whatever an injected instruction persuades the model to ask for, the answer is computed from the policy, the arguments and the budget. The decision, the reason and the policy version go into the evidence record.

Identity & Authorisation

Purpose

Every agent, and every tool call it makes, acts under an identity of its own with the least privilege the task needs. If the model is steered, identity and scope decide how far the damage can go, and the record of who acted decides whether you can prove what happened.

Rules

  • One identity per agent, never a shared service account. A shared account makes every agent as powerful as the most privileged one, and makes actions impossible to attribute.
  • Short-lived, scoped tokens. Issue a credential for one task and one audience (a single tool or server), with a life of minutes. No standing keys.
  • The user's authority is not silently inherited. When an agent acts for a person, that is an explicit delegation. The token names both the person and the agent acting for them, and its scope is narrowed to the task, never the person's whole session. OAuth 2.0 Token Exchange (RFC 8693) defines this kind of delegation, including an actor claim that records who is acting.
  • Authorise each tool call, outside the model. The runtime checks the call against the agent's identity, the person it acts for and the scope of the task. The model asks. It does not decide.
  • No token pass-through. A tool server accepts only tokens issued for it and never forwards a caller's token downstream. The MCP specification requires this of MCP servers.
  • Keep credentials out of the context window. The runtime attaches them at the tool boundary. A secret the model can read is a secret an injected instruction can ask for.

Evidence

Every decision and action leaves a record: who or what acted (the agent's identity, the model and its version), on whose behalf, with which inputs (the arguments, and which tool results and documents were in context), under which policy (its version, and whether the action was allowed, denied, or approved and by whom), and the outcome. Records are append-only. Each carries the hash of the one before it, so that an edited or removed record is detectable, and they are stored where the agent's own credentials cannot change them.

Runnable as written: Python 3.10 or later, standard library only. Run for this page in November 2026.

import hashlib, json def digest(record): body = {k: v for k, v in record.items() if k != "hash"} data = json.dumps(body, sort_keys=True).encode() return hashlib.sha256(data).hexdigest() def append_record(chain, record): record = dict(record) record["prev"] = chain[-1]["hash"] if chain else "genesis" record["hash"] = digest(record) chain.append(record) def verify(chain): prev = "genesis" for record in chain: if record["prev"] != prev: return False if record["hash"] != digest(record): return False prev = record["hash"] return True chain = [] append_record(chain, { "actor": "agent:invoice-reader", "on_behalf_of": "user:4821", "tool": "send_email", "args": {"to": "cfo@example.com"}, "context": ["doc:inv-0093.pdf", "tool:search_docs#2"], "policy": "2026-11-a", "decision": "allow", "approved_by": "approver-17", }) print(verify(chain)) # True chain[0]["args"]["to"] = "x@attacker.test" print(verify(chain)) # False: the edit shows

What this does not stop

An agent that is correctly authenticated, and has been steered, will misuse the privileges it legitimately holds. This is the confused deputy problem. Identity and scope limit how much it can do and make the action attributable. They do not make the action right.

A scope is only as narrow as it is defined: "send email" still means email to anyone unless the tool boundary checks the recipient. And evidence is a detective control. It stops nothing at the time, and it proves little unless someone reviews it and the latest hash of the chain is kept somewhere the agent cannot reach, since a chain rewritten from the start still verifies.

How it is done today

Still emerging: W3C Decentralized Identifiers (DIDs) and Verifiable Credentials for agent identity across organisations (ANP builds on them), and several IETF Internet-Drafts on agent identity. None of these is yet a settled standard for agents. Watch them; do not build on them unexamined.

Cost Governance

Purpose

Cost is one of the main reasons agent projects are stopped. In June 2025 Gartner predicted that over 40% of agentic AI projects will be cancelled by the end of 2027, naming escalating costs alongside unclear business value and inadequate risk controls (Gartner press release, 25 June 2025).

Implement per-step cost tracking, a budget cap per goal and an automatic kill switch. Monitor the ratio of value to cost: if the agent has spent more than the task is worth, stop and escalate. A budget cap is also a security control, because it bounds what a steered or looping agent can burn.

Budget enforcement

class CostGovernor: def check(self, state): if state.total_cost > self.budget: state.kill("budget_exceeded") if state.cost_per_step > self.per_step_limit: self.alert("cost_anomaly") if state.total_cost > 0: ratio = state.value_delivered / state.total_cost if ratio < self.min_ratio: self.escalate_to_human()

Purpose
