Most tools listed are open source or source-available. The few that are commercial or proprietary carry a label. Licences change, so read a project's licence before you use it at work. Each worked example is illustrative, not an account of a real incident.

The eight stages

Quick win: Deploy OWASP Juice Shop and run your first team capture-the-flag session within a week.

Key activities

  • Security onboarding and OWASP Top 10 training Essential
  • Secure coding guidelines and standards adoption Essential
  • Role-based training tracks (developers, QA, architects, product managers) Recommended
  • Security champions programme within development teams Recommended
  • Capture-the-flag exercises and war games Advanced
  • Periodic refreshers on the CWE Top 25 Advanced

Worked example (illustrative)

A team of twelve replaces its annual slide deck with a two-hour hands-on session each quarter. In the first one, developers attack a deliberately vulnerable shop application, and three of them reach the same SQL injection by different routes. The team then searches its own code for the same pattern, queries built by joining strings, and finds two. Both are fixed that week, and parameterised queries go on the code review checklist.

Tools

  • OWASP WebGoatDeliberately insecure Java application with guided lessons.
  • OWASP Juice ShopDeliberately vulnerable JavaScript web shop with scored challenges.
  • DVWADeliberately vulnerable PHP application for practising common attacks.
  • Hack The BoxHosted penetration-testing labs. commercial
  • SecureFlagHands-on secure coding labs. commercial
  • TryHackMeGuided security learning paths in the browser. free plan, paid plans

Quick win: Draw your first threat model in OWASP Threat Dragon. One data-flow diagram of one feature is enough to start.

Key activities

  • Threat modelling (STRIDE) Essential
  • Compliance mapping (GDPR, DPDP Act, PCI DSS, SOC 2, HIPAA) Essential
  • Security risk assessment and data classification Recommended
  • Abuse case and misuse case development Recommended
  • Security-focused user stories and acceptance criteria Advanced
  • Privacy impact assessments Advanced

Worked example (illustrative)

A product owner writes the story "a customer can download past invoices". The team adds an abuse case, "a logged-in customer changes the invoice number in the address to read someone else's invoice", and turns it into an acceptance criterion: the server checks that the invoice belongs to the caller and answers "not found" if it does not. Because invoices hold personal data, the story is also tagged for the privacy assessment. The criterion becomes an automated test before any code is written.

Tools

  • OWASP Threat DragonDiagram-based threat modelling, as a desktop or web application.
  • ThreagileAgile threat modelling toolkit: the architecture is described in a YAML file and checked against risk rules.
  • OWASP ASVSApplication Security Verification Standard, a catalogue of testable security requirements (version 5.0.0, May 2025).
  • OWASP CornucopiaCard game that helps a team identify security requirements.
  • pytmThreat modelling written as Python code.

Quick win: Bookmark the OWASP Cheat Sheet Series and use it as your design reference.

Key activities

  • Attack surface analysis and reduction Essential
  • Secure design patterns (defence in depth, least privilege, fail-safe defaults) Essential
  • Cryptographic standards and protocol review Recommended
  • Authentication and authorisation framework selection Recommended
  • Zero Trust architecture principles Advanced
  • Architecture risk analysis and formal design review Advanced

Worked example (illustrative)

While drawing the data flow for a file-upload feature, the team marks the trust boundary between the browser and the storage service. Applying STRIDE to that boundary gives a tampering threat: the first design let the browser choose the storage path, so one user could overwrite another user's file. The design changes: the server generates the object name, issues a short-lived upload address limited to that one object, and scans the file before anyone can fetch it. The finding and the decision are recorded beside the diagram.

Tools

  • Microsoft Threat Modeling ToolThreat modelling on data-flow diagrams, with STRIDE applied to each element. proprietary
  • OWASP Threat DragonDiagram-based threat modelling, as a desktop or web application.
  • draw.ioDiagramming tool for architecture and data-flow diagrams (formerly diagrams.net).
  • OWASP Cheat SheetsShort, practical guidance on specific security topics.

Quick win: Add Semgrep and Gitleaks to your pre-commit hooks today, so obvious flaws and committed secrets are caught before they leave the laptop.

Key activities

  • Static application security testing (SAST) Essential
  • Secret detection in repositories and commits Essential
  • Pre-commit hooks for automated checks Essential
  • Software composition analysis (SCA) Recommended
  • Peer code review with a security checklist Recommended
  • AI-generated code held to the same scans and review as any other code Recommended

Worked example (illustrative)

A developer commits a configuration file that still contains a cloud access key. The pre-commit secret scan blocks the commit on the laptop, so the key never reaches the shared repository. The developer still treats the key as exposed: it is revoked and reissued, and the value moves to the secrets manager, with only a reference left in the file. Had the key reached the shared repository, deleting the commit would not have been enough, because only rotating the key makes a leaked copy useless.

Quick win: Run the ZAP baseline scan against your staging environment. It spiders the site and scans passively, with no active attacks.

Key activities

  • Dynamic application security testing (DAST) Essential
  • Manual and automated penetration testing Essential
  • Interactive application security testing (IAST) Recommended
  • API security validation and contract testing Recommended
  • Fuzz testing for unexpected inputs Advanced
  • Regression security testing in CI/CD Advanced

Worked example (illustrative)

A nightly dynamic scan of the staging site reports that the session cookie is set without the Secure and HttpOnly flags, and that an error page prints a stack trace. Neither is a false positive, so both become tickets with the scan evidence attached. The fixes are a few lines of framework configuration. The team then adds both checks to the scan's fail list, so a regression breaks the build instead of waiting for the next penetration test.

Quick win: Add Trivy to your CI pipeline: it scans container images, dependencies and infrastructure code. Pin it, like every third-party pipeline step, to a commit SHA or an image digest.

Key activities

  • Container and infrastructure image scanning Essential
  • CIS Benchmark hardening checks Essential
  • Infrastructure-as-Code (IaC) security validation Recommended
  • CI/CD pipeline security gates Recommended
  • SBOM generation, artefact signing and build provenance Advanced

Worked example (illustrative)

The image scan gate fails a release: the base image carries a critical vulnerability in a system library, and a fixed version exists. The team does not override the gate. They rebuild on the patched base image, pin it by digest, and the next pipeline run passes. For a finding that has no fix yet, the agreed route is a time-limited exception with a named owner, never a silent skip.

Quick win: Deploy Wazuh on a test host. One open-source platform covers log analysis, intrusion detection, file integrity monitoring and configuration assessment.

Key activities

  • SIEM: log aggregation and correlation Essential
  • Vulnerability scanning of live systems Essential
  • Runtime anomaly and intrusion detection Recommended
  • Network traffic analysis and IDS/IPS Recommended
  • Proactive threat hunting Advanced
  • Continuous patch management Advanced

Worked example (illustrative)

An alert fires at night: one service account has failed to log in several hundred times in five minutes, from an address the company has never seen. The on-call engineer confirms in the logs that no attempt succeeded, blocks the address and rotates the account's credential. Next morning the team finds that the same rule had been firing for weeks on a noisy health check and had been muted on some hosts. They fix the health check and remove the mute, so the alert can be trusted again.

Quick win: Write a one-page incident response plan and rehearse it in a table-top exercise. An open-source case tool such as DFIR-IRIS can track the cases.

Key activities

  • Incident response playbook execution (NIST SP 800-61 Rev. 3) Essential
  • Digital forensics and evidence preservation Essential
  • Stakeholder and regulatory notification (CERT-In within 6 hours, GDPR within 72 hours) Recommended
  • Blameless post-incident retrospectives Recommended
  • Secure data disposal and API retirement Advanced
  • Automated SOAR orchestration and threat intelligence sharing Advanced

Worked example (illustrative)

A customer reports seeing another customer's order. The incident lead opens a case, the team switches off the faulty cache rule within the hour and preserves the logs that show which records were exposed. Because personal data is involved, legal deadlines start: an organisation in India reports a listed incident type to CERT-In within 6 hours of noticing it, and under the GDPR the supervisory authority is told within 72 hours of becoming aware. A week later a blameless review traces the cause to a cache key that left out the customer ID, and a test for that case joins the stage 5 suite.

Key metrics & KPIs

What to measure to show that your Secure SDLC is working. The targets are example starting points, not industry benchmarks: set your own from your risk appetite and the rules you fall under.

Mean time to remediate (MTTR)

Average time from vulnerability detection to verified fix across all severity levels.

Example target: critical within 24 hours, high within 7 days, medium within 30 days. For comparison, PCI DSS v4.0.1 (requirement 6.3.3) allows one month from release for patches to critical vulnerabilities.

Vulnerability escape rate

Percentage of vulnerabilities found in production compared with pre-production (shift-left effectiveness).

Example target: fewer than 10% escaping to production

SAST/DAST coverage

Percentage of codebases and applications actively scanned by automated security tools.

Example target: more than 95% of repositories with SAST enabled

Security gate pass rate

Percentage of builds that pass all security gates on first attempt without overrides.

Example target: more than 85% passing first time

Mean time to detect (MTTD)

Average time between a security event occurring and being detected by monitoring.

Example target: under 1 hour for critical events

Dependency currency

Percentage of third-party dependencies that are within one major version of the latest release.

Example target: more than 80% current, no known critical CVEs

Training completion rate

Percentage of engineering staff who completed security training in the past 12 months.

Example target: 100% each year

Incident response time

Time from incident declaration to containment achieved, measured per severity.

Example target: a priority 1 incident contained within 4 hours

What each reference says

01 Training and awareness
  • NIST SSDF: PO.2.2, role-based training for everyone whose work contributes to secure development.
  • OWASP SAMM: Education and Guidance (Governance), with its streams Training and Awareness, and Organization and Culture.
  • ISO/IEC 27001:2022: A.6.3, Information security awareness, education and training.
  • PCI DSS: 6.2.2, people who develop bespoke and custom software are trained at least once every 12 months; 12.6.1, a formal security awareness programme.
  • SOC 2: CC1.4 (attracting, developing and retaining competent people) and CC2.2 (internal communication). Their points of focus name technical training and a security awareness training programme.
  • HIPAA: 45 CFR 164.308(a)(5)(i), a security awareness and training programme for the whole workforce.
  • No specific clause: GDPR (it has no training article; Art. 39(1)(b) only makes monitoring of staff training one of the data protection officer's tasks); India.
02 Security requirements
  • NIST SSDF: PO.1, Define Security Requirements for Software Development.
  • OWASP SAMM: Security Requirements (Design) and Policy and Compliance (Governance).
  • ISO/IEC 27001:2022: A.5.8, Information security in project management; A.8.26, Application security requirements.
  • PCI DSS: 6.2.1, bespoke and custom software is developed securely, with security considered at each stage of the lifecycle. This is the nearest fit: PCI DSS does not say how requirements are gathered.
  • SOC 2: CC3.2, identify and analyse risks to the organisation's objectives. One point of focus covers identifying threats.
  • GDPR: Art. 35(1), a data protection impact assessment before processing that is likely to result in a high risk.
  • HIPAA: 45 CFR 164.308(a)(1)(ii)(A), risk analysis.
  • No specific clause: India.
03 Secure design
  • NIST SSDF: PW.1, design software to meet security requirements and mitigate security risks (task PW.1.1 names threat modelling); PW.2, review the design against those requirements.
  • OWASP SAMM: Threat Assessment and Secure Architecture (Design), and Architecture Assessment (Verification).
  • ISO/IEC 27001:2022: A.8.25, Secure development life cycle; A.8.27, Secure system architecture and engineering principles.
  • SOC 2: CC8.1, the change-management criterion, which covers designing changes to software and infrastructure.
  • GDPR: Art. 25, data protection by design and by default; Art. 32(1)(a), pseudonymisation and encryption of personal data.
  • HIPAA: 45 CFR 164.312(a) to (e), the technical safeguards a design has to provide: access control, audit controls, integrity, person or entity authentication and transmission security.
  • India: DPDP Act, 2023, s. 8(5), reasonable security safeguards; DPDP Rules, 2025, Rule 6 sets the minimum, including encryption or masking and access control. Both come into force in May 2027.
  • No specific clause: PCI DSS (no requirement names threat modelling or a design review).
04 Secure coding
  • NIST SSDF: PW.5, follow secure coding practices; PW.7, review or analyse the code (its examples include peer review and static analysis); PW.4 (task PW.4.4), verify third-party components; PS.1, protect code from unauthorised access and tampering. SSDF does not mention secret scanning.
  • OWASP SAMM: Secure Build (Implementation), with its streams Build Process and Software Dependencies; Secure Deployment, stream Secret Management.
  • ISO/IEC 27001:2022: A.8.28, Secure coding; A.8.4, Access to source code.
  • PCI DSS: 6.2.3, code is reviewed before release; 6.2.4, engineering techniques that prevent or mitigate common software attacks; 6.3.2, an inventory of bespoke software and the third-party components in it.
  • SOC 2: CC8.1, which covers developing changes.
  • No specific clause: GDPR; HIPAA; India.
05 Security testing
  • NIST SSDF: PW.8, test executable code to find vulnerabilities. Its examples include dynamic testing, fuzz testing and penetration testing.
  • OWASP SAMM: Security Testing and Requirements-driven Testing (Verification).
  • ISO/IEC 27001:2022: A.8.29, Security testing in development and acceptance.
  • PCI DSS: 11.4.1 to 11.4.3, a penetration testing methodology, and internal and external penetration tests at least once every 12 months.
  • SOC 2: CC8.1 covers testing changes; CC4.1 (ongoing and separate evaluations) has a point of focus that names penetration testing.
  • GDPR: Art. 32(1)(d), a process for regularly testing, assessing and evaluating the effectiveness of security measures.
  • HIPAA: 45 CFR 164.308(a)(8), periodic technical and non-technical evaluation.
  • No specific clause: India.
06 Secure deployment
  • NIST SSDF: PO.4, define and use criteria for software security checks (the basis of a release gate); PS.2, a way to verify the integrity of a release, such as signing; PS.3, archive and protect each release (task PS.3.2 covers provenance data such as an SBOM); PW.9, secure settings by default. SSDF covers the software you ship, not the hardening of production hosts.
  • OWASP SAMM: Secure Deployment (Implementation), stream Deployment Process; Environment Management (Operations), stream Configuration Hardening.
  • ISO/IEC 27001:2022: A.8.9, Configuration management; A.8.31, Separation of development, test and production environments; A.8.32, Change management.
  • PCI DSS: 2.2.1, configuration standards; 6.5.1, change procedures for production; 6.5.3, pre-production separated from production; 6.5.6, test data and test accounts removed before go-live.
  • SOC 2: CC8.1, which covers approving and implementing changes.
  • No specific clause: GDPR; HIPAA; India.
07 Operations and monitoring
  • NIST SSDF: RV.1, identify and confirm vulnerabilities on an ongoing basis; RV.2, assess, prioritise and remediate them. Both concern the software you produce, not the scanning of live hosts.
  • OWASP SAMM: Environment Management (Operations), stream Patching and Updating; Incident Management, stream Incident Detection.
  • ISO/IEC 27001:2022: A.8.8, Management of technical vulnerabilities; A.8.15, Logging; A.8.16, Monitoring activities.
  • PCI DSS: 6.3.1, vulnerabilities are identified and risk-ranked; 6.3.3, patches for critical vulnerabilities within one month of release; 10.4.1, audit logs reviewed at least once a day; 11.3.1, internal vulnerability scans at least once every three months; 11.5.1, intrusion detection or prevention.
  • SOC 2: CC7.1, detect new vulnerabilities and configuration changes that introduce them; CC7.2, monitor system components for anomalies.
  • GDPR: Art. 32(1)(b), the ongoing confidentiality, integrity, availability and resilience of processing systems and services.
  • HIPAA: 45 CFR 164.312(b), audit controls; 164.308(a)(1)(ii)(D), information system activity review.
  • India: CERT-In Directions of 28 April 2022: (i) clocks synchronised to the NIC or NPL time servers, and (iv) logs of all ICT systems kept for a rolling 180 days within India. DPDP Rules, 2025, Rule 6(c) and (e): access logs, monitoring and one year of log retention, in force from May 2027.
08 Incident response and decommissioning
  • OWASP SAMM: Incident Management (Operations), stream Incident Response; Operational Management, stream System Decommissioning / Legacy Management.
  • ISO/IEC 27001:2022: A.5.24 to A.5.28, incident management from planning and preparation to learning and the collection of evidence; A.8.10, Information deletion; A.7.14, Secure disposal or re-use of equipment.
  • PCI DSS: 12.10.1, an incident response plan that is ready to be activated; 3.2.1, data retention and disposal; 9.4.7, electronic media holding cardholder data is destroyed when no longer needed.
  • SOC 2: CC7.3, evaluate security events; CC7.4, respond to incidents; CC7.5, recover from them; CC6.5, protections over a retired asset are removed only once its data can no longer be read.
  • GDPR: Art. 33, tell the supervisory authority within 72 hours of becoming aware of a personal data breach; Art. 34, tell the people affected when the risk to them is high; Art. 5(1)(e), storage limitation.
  • HIPAA: 45 CFR 164.308(a)(6), security incident procedures; 164.310(d)(2)(i), disposal. Breach notification is a separate rule: 164.404 (individuals) and 164.408 (the Secretary).
  • India: CERT-In Directions of 28 April 2022, (ii): report the listed incident types within 6 hours of noticing them. DPDP Act, 2023, s. 8(6) with Rule 7: tell the Board and each affected person without delay, with a detailed report to the Board within 72 hours; s. 8(7): erase personal data once its purpose is served. The DPDP provisions come into force in May 2027.
  • No specific clause: NIST SSDF (it has no incident response practice and nothing on decommissioning; use NIST SP 800-61 Rev. 3 for response and SP 800-88 Rev. 2 for media sanitisation).

How this was checked

  • Checked on 18 November 2026. NIST SSDF, OWASP SAMM, the GDPR, HIPAA, the DPDP Act and Rules and the CERT-In Directions were read in the publishers' own texts.
  • PCI DSS, ISO/IEC 27001 and the SOC 2 Trust Services Criteria are licensed documents. PCI DSS and SOC 2 references were checked against published reproductions of the requirements, and ISO control titles against a national standards body's contents list for ISO/IEC 27002:2022. Read the licensed text before you rely on a reference in an audit.
  • NIST SSDF version 1.1 and NIST SP 800-218 are the same document (February 2022). Version 1.2 (SP 800-218 Rev. 1) is still a draft, published in December 2025.
  • ISO/IEC 27001 references use the 2022 edition. The 2013 edition's A.14 (system acquisition, development and maintenance) became A.5.8 and A.8.25 to A.8.33.
  • SOC 2 points of focus are illustrations of a criterion, not requirements in themselves.
  • India: the DPDP Act's duties on security safeguards, breach intimation and erasure (section 8) and Rules 6 and 7 come into force in May 2027. The CERT-In Directions of 28 April 2022 are in force now.

SBOMSoftware Bill of Materials: an inventory of every component in a release
SIEMSecurity Information and Event Management

IaCInfrastructure as Code: infrastructure defined in version-controlled files

CSPMCloud Security Posture Management

RACIResponsible, Accountable, Consulted, Informed: an ownership matrix
